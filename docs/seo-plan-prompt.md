# SEO改善計画を作らせるためのプロンプト

kurofukubo の検索流入を増やす計画を、95点（100点満点）が出るまで反復して作らせるための指示書。

**背景**: 過去4回の試行が 51 / 53 / 48 / 52点で不合格。毎回**別の理由**で落ちており、点数が上がらなかった。原因は計画を書く力ではなく、**着手前の事実確認と、出した数値の検算を怠ったこと**にある。このプロンプトはそれを構造的に防ぐ。

---

## 使い方

1. 下の「## 指示」以降をそのまま渡す
2. 計画が出てきたら、「## 採点ルーブリック」を別のレビュアー（サブエージェント等）に渡して採点させる
3. 95点未満なら、指摘とともに差し戻す
4. **同じ誤りが2回続いたら、そこで止めて人間が判断する**

---

## 指示

あなたは kurofukubo（複式簿記の家計簿SaaS）の検索流入を増やす計画を作る。

### 絶対に守ること

**1. 計画を書く前に、§A のチェックリストを全項目埋めること。** 埋まっていない項目がある状態で施策を書いてはいけない。埋められなかった項目は「未確認」と明記し、それに依存する施策は提案しない。

**2. 数値を出したら必ず検算し、検算結果も計画に載せること。** §B のルールに従う。

**3. 因果を主張しないこと。** 「Xしたから順位が上がった」と書けるのは、git履歴で X 以外の変更が無いことを確認し、かつクロール日が X の後であることを確認した場合のみ。それ以外は「Xの後に上がった」と書く。

**4. 検出力を先に計算すること。** 「この施策の効果は、現在のサンプルサイズで検出できるか」を計算し、できないなら**因果推定を目的にしない設計**にする。できないものをできるように見せかけない。

**5. 過去4回の失敗を繰り返さないこと。** §C の禁止事項を守る。

---

### §A. 着手前に確定させる事実（全項目必須）

計画の冒頭に、この表を埋めた形で載せること。

| # | 確認事項 | 確認方法 | 結果 |
|---|---|---|---|
| A1 | 対象ページの**現在の本文**に、狙う語・セクションが既に存在しないか | ファイルを実際に開いて全文読む | |
| A2 | 対象ページの**直近の変更履歴**（何を、いつ、どのコミットで） | `git log --format="%h %ad %s" --date=format:"%m/%d %H:%M" -- <path>` | |
| A3 | その変更は**本文か、タイトル/metaか** | `git show <sha> -- <path>` で追加行を分類 | |
| A4 | 対象ページの**最終クロール日** | Coverage エクスポート。変更日より前なら**未反映** | |
| A5 | 対照にする気なら、その**対照ページも同じコミットで変更されていないか** | `git show <sha> --stat --name-only` | |
| A6 | 狙うクエリの**現在の表示回数・順位・クリック** | GSC クエリ.csv | |
| A7 | その表示回数で、狙う変化を**検出できるか**（検出力計算） | §B4 | |
| A8 | 対象ページからアプリへの**実流入があるか** | CloudFrontログ。§D2 の注意を読むこと | |

**A4 が「未反映」だった場合、そのページへの追加変更を提案してはいけない。** まず再クロールを待つ。これは過去2回落ちた原因である。

---

### §B. 数値の検算ルール

**B1. 部分は全体を超えない。** 部分集合の合計を出したら、必ず全体と比較して載せる。

> 過去の失敗例: 「順位10以内の合計460表示」と書いたが、サイト全体は457表示だった。原因はページ次元とクエリ次元を足したこと。**GSCの「ページ」と「クエリ」は同じ表示を別の切り口で数えている。足してはいけない。**

**B2. イベント数は上限を超えない。** 経路別・セグメント別の内訳を出したら、各列の合計が**そのイベントの distinct 総数以下**であることを確認して載せる。

> 過去の失敗例: 経路別「登録」列の合計が11だったが、`registered` を出した distinct IP は6件しかなかった。原因は**同じIPが複数の経路バケットに入っていた**こと。バケットは相互排他にするか、重複を明示すること。

**B3. 窓を揃える。** 期間の違うデータを比較するときは必ず日割りにする。

> 過去の失敗例: 「19表示 → 222表示、一桁増えた」と書いたが、19は7日窓、222は28日窓。日割りでは 2.71→7.93/日（2.9倍）。

**B4. 検出力を計算する。** CTRや率の変化を検出したいなら、必要サンプル数を出す。目安として、CTR を p1→p2 に変える検出（α=0.05両側・検出力80%）には概ね `16 × p̄(1-p̄) / (p2-p1)²` 表示が要る。**現在の表示回数がそれに満たないなら、その指標を合否判定に使ってはいけない。**

**B5. 使ったスクリプトを残す。** 数値を出したスクリプトのパスを計画に書く。再検算できない数値は載せない。

---

### §C. 禁止事項（過去4回で実際に起きた失敗）

- **C1** 対象ファイルを読まずに「新規セクションを追加する」と書くこと（v1・v3で発生。実際は既存だった）
- **C2** 同じコミットで変更されたページを対照群にすること（v2で発生。`b90f936` はLP 24ページを同時変更している）
- **C3** 未クロールの変更が待機している対象に、さらに変更を重ねること（v3で発生）
- **C4** 満たすことが算術的に不可能な合格条件を書くこと（v1・v3で発生。例:「順位10以内かつ表示100かつクリック10」は順位10のCTR 2〜3%と矛盾する）
- **C5** 「効果の証明ではない」と断りつつ、その指標で因果的な意思決定（他テーマへの展開可否など）を決めること（v4で発生）
- **C6** 無施策でも達成される水準を合格ラインにすること（v4で発生。「順位維持だけで20〜30見込める」と書いた上で30を合格ラインにした）
- **C7** 外部の検索需要データ（Keyword Planner / Google Trends 等）や実際のSERPを一度も見ずに、需要や競合を推定すること
- **C8** 自サイトで実証されている施策を禁止し、実証のない施策を選ぶこと（v4で発生。§D3 参照）

---

### §D. データソースと既知の落とし穴

**D1. Search Console**
- エクスポートは **page と query を結合しない**。「このページのこのクエリの順位」はUIでページ絞り込みをしないと取れない
- クエリ.csv は**全表示の約3割しかカバーしない**（残りは匿名化）。「最大のクエリ」は可視分に限った話
- ページ表とデバイス表で合計が違う（457 vs 432）。どちらを使うか明記する
- データ反映に**2〜3日の遅延**がある

**D2. CloudFrontログ**（`scripts/admin/.cache-cflogs/`）
- 日付列は **UTC**。`server.mjs` は JST に変換して集計している（`jstDay()`）
- ボット除外は3段階: UA正規表現、`isOutdatedUa`（Chrome<110 / iOS<15）、self判定（`selftest` クエリ＋既知プレフィックス）。**`isOutdatedUa` を忘れると、Tencent Cloud 発の iOS 13 偽装クローラーを実ユーザーとして数える**
- **実ユーザーの判定は `/_e/app_open` の有無**。`/` への着地だけではJSを実行しないクローラーが混ざる
- `registered` イベントは「その端末で初めてログインした」であり**登録数ではない**。`server.mjs` にもその旨のコメントがある。登録数は Cognito の `UserCreateDate` を正とする
- IPは端末の代わりにならない。IPv6はローテーションし、日をまたぐ名寄せに使えない（直近12日で2日以上出現したIPは50件中4件）

**D3. 自サイトで実証されている施策**

`guide-furusato.html` は **7/1 のタイトル・meta 変更のみ**（`d136373`、本文は実質0行）で、表示 2.71/日 → 7.93/日（2.9倍）、順位 8.26 → 5.85 になった。

**このサイトで効果が確認できている唯一の施策はタイトル/meta の最適化である。** 本文加筆で順位が上がった実証はまだ無い。加筆を提案するなら、その理由を明示すること。

### §F. 計画に必ず含める項目

1. §A のチェックリスト（全項目）
2. 対象の選定理由と、**却下した代替案とその理由**
3. 施策の内容（既存要素と重複しないことを A1 で確認済みであること）
4. **検出力の計算**（§B4）と、それを踏まえた判定設計
5. 合格条件。**無施策でも達成される水準になっていないこと**（C6）
6. 撤退条件
7. リスクと対処
8. やらないこと
9. 変更時のチェックリスト（title / description / og / twitter / JSON-LD / sitemap lastmod / 再クロール申請）
10. 使った検算スクリプトのパス

## 採点ルーブリック（レビュアーに渡す）

以下の配点で100点満点。**根拠のない減点はしないこと。厳しく採点すること。**

| 観点 | 配点 | 満点の条件 |
|---|---|---|
| **事実の正確さ** | 30 | 計画中の全数値が一次データで再現できる。§A が全項目埋まっている。既存要素を新規と誤認していない |
| **検算の実施** | 15 | §B1〜B5 が守られている。部分と全体、イベント上限、窓の統一、検出力が明示されている |
| **因果主張の慎重さ** | 10 | git履歴とクロール日を確認せずに因果を主張していない。未クロールの変更に重ねていない |
| **判定設計** | 20 | 合格条件が算術的に成立する。無施策で達成される水準でない。検出力に見合っている。因果を主張しないなら意思決定もそれに従っている |
| **対象選定** | 10 | 期待値と測定可能性の両方で比較され、代替案の却下理由がある |
| **リスク** | 10 | 見落としが少ない。特に季節性・カニバリ・再クロール・重複コンテンツ |
| **実行可能性** | 5 | 個人開発者が実行できる粒度。チェックリストに漏れがない |

**採点時に必ず確認すること**

- 計画が「新規に追加する」と書いた要素が、**本当に既存ファイルに無いか**（過去2回ここで落ちている）
- 内訳の合計が、対応するイベントの distinct 総数を**超えていないか**
- 部分集合の合計が**全体を超えていないか**
- 合格条件を**満たせる組み合わせが実在するか**（算術チェック）
- 対照群に指定したページが、**切り分けたい変更で一緒に変更されていないか**

**出力**: 点数と観点別内訳、減点理由（具体的に）、95点にするために直すこと（優先度順）、事実誤認の指摘。

---

## 停止条件

- **95点以上** → 合格。実行に移る
- **同じ種類の誤りが2回続いた** → 停止。人間が判断する
- **4回試行して点数が上がらない** → 停止。計画作成ではなく、§E の「未確定」項目を人間が外部ツールで埋めることを優先する
