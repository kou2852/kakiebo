# 計測イベントとアプリ機能の不整合 — 調査結果と修正計画（2026-08-02）

計測（`utils/track.js` と各呼び出し元）と、アプリの実際の機能の間にズレがないかを調査した。
**本ドキュメントは調査と計画のみ。コードは変更していない。**

検証スクリプト: `docs/design-gen/verify-event-consistency.mjs`（ローカルの `vite preview` に対して実行）

---

## A. 実機で再現した不整合（3件）

### A-1【重大】口座を登録しただけで「初回記帳」になる

```
■ 口座を残高付きで登録しただけ（取引は一切していない）
   発火: first_journal journal_added
```

`AccountModal.jsx:89` と `AccountsPage.jsx:126` は、残高を入力して口座を作ると
「開始残高（○○）」という仕訳を `addJournal()` で作る。`addJournal` の先頭で
`trackOnce('first_journal')` を呼んでいるため、**取引を1件も記帳していない人が
「記帳到達」として数えられる**。

影響が大きいのは、**ガイドツアーの口座登録ステップ（④）で必ずこれが起きる**こと。
ツアーを進めた人は全員、記帳ステップ（⑤⑥）に到達する前に「初回記帳」を踏む。

- ファネルの「初回記帳」が実態より多く出る
- ゲストの記帳回数（`journal_added`）にも同じ仕訳が乗る
- 「記帳まで到達した人」という指標が、実質「口座を登録した人」に近くなる

簿記としては開始残高も正しい仕訳なので、**バグではなく指標の定義の問題**。

### A-2【中】サンプルを見ただけで「完走かつ記帳」になる

```
■ 「サンプルで見る」→ そのままツアー完走
   発火: tour_done_acted
   → 記帳していないのに tour_done_acted: はい（誤り）
```

`Tour.jsx:215,229` は完走時に `journals.length > journalsAtTourStart.current` で
「実際に記帳したか」を判定している。しかし `trySample()`（`Tour.jsx:233`）が
`loadSampleData()` でサンプル仕訳を10件投入するため、件数が増えて **記帳したと誤判定** される。

コメントに「偽の完走を区別」とあり、まさにその意図が達成できていない。

### A-3【中】ファネルの段が入れ子になっていない

```
■ LP経由（?guest）の人がログイン画面を通るか
   発火: app_open app_first guest_start guest_first
   → auth_view: 通らない
```

`?guest` 付きで来た人は `AuthPage` を経ずにアプリへ入るため `auth_view` が出ない。
つまり **「ログイン画面を見た」は「ゲスト開始」の上位集合ではない**。

現在のダッシュボードは5段を縦に並べ「前段比」を出しているが、
`auth_view → guest_first` の前段比は意味を持たない（別経路の人数を割っている）。
同様に、直接メール登録した人は `guest_first` を通らずに `registered` へ行く。

## B. コード読解で判明した不整合（4件）

### B-1【中】「ゲスト開始した人のうち記帳まで到達」の分子と分母が揃っていない

`server.mjs` の `journalOfGuest = first_journal / guest_first`。
しかし `first_journal` は **登録ユーザーでも発火する**（`DataContext.jsx` で `guestMode` の
判定より前に呼んでいる）のに対し、`guest_first` はゲストのみ。
分子に非ゲストが混ざるため、率が過大に出る。理論上100%を超えうる。

### B-2【小】アクティベーションの分母が「回数」

`activation = journal_added / guest_start`。`guest_start` は `?guest` 付きで来るたびに
発火するため、同じ人がLPから何度も入ると分母だけ膨らむ。
`journal_added` もゲスト限定の回数なので単位は揃っているが、
**「人あたり」ではなく「訪問あたり」の指標**である点が画面から読み取れない。

### B-3【小】バックアップ復元では初回記帳が出ない

`importAll()`（`DataContext.jsx:324`）は `addJournal` を通さず `applyAll` で一括反映する。
500件復元しても `first_journal` は出ず、その後の手入力1件目で初めて出る。
実害は小さいが、「初回記帳」の定義が経路によって変わる。

### B-4【小】チャンク404の自動リロードで `app_open` が二重に出る

`main.jsx` の `vite:preloadError` ハンドラがリロードするため、その分 `app_open` が1回増える。
発生頻度は低く、`app_first` は二重にならないので影響は限定的。

## C. 仕様上の制約（修正不要・時間で解消）

- `retain_d1/d7/d30` は「本当の初回利用日」ではなく **計測開始（2026-08-02）以降の再訪** を測っている。
  `kk_first_seen` が導入時点で誰にも無いため。README に記載済み。
- 同じ理由で、最初の数日は `app_first` / `first_journal` に既存利用者の分が上乗せされる。
- localStorage を消した人・別端末の人は別人として数える。IPベースより正確だが完全ではない。

## D. 修正計画

### 方針

**「記帳到達」の定義を「ユーザーが取引を記帳したこと」に統一する。**
口座の開始残高やサンプル投入は、簿記上は仕訳でも「使い始めた」の指標としては別物として扱う。

### D-1. 開始残高を計測対象から外す（A-1 の修正）

`addJournal(data, opts)` に第2引数を足し、`opts.silent` のときは `trackOnce('first_journal')` と
`track('journal_added')` を呼ばない。

- 変更: `contexts/DataContext.jsx`（`addJournal` のシグネチャ）
- 呼び出し側: `AccountModal.jsx:89` と `AccountsPage.jsx:126` に `{ silent: true }` を渡す
- **摘要の文字列（「開始残高（」で始まる）で判定する案は採らない。** ユーザーが同じ摘要を
  手入力したときに巻き込まれるため

判断が必要な点: `journal_added`（ゲストの記帳回数）も除外してよいか。
除外すると過去データとの連続性は崩れるが、指標としては一貫する。**除外を推奨。**

### D-2. ツアーの完走判定からサンプルを除く（A-2 の修正）

`Tour.jsx:215,229` の比較を、サンプル以外の仕訳数で行う。

```
const realCount = () => journals.filter((j) => !j.sample).length;
```

`journalsAtTourStart.current` も同じ基準で記録する（`Tour.jsx:243`）。
D-1 を入れると開始残高も `sample` ではないため件数に残る点に注意。
**D-1 と揃えるなら、ツアー中に作られた開始残高も「記帳した」に含めない**のが一貫する。
その場合は仕訳に「計測対象外」の印を付ける方式（下記の代案）が必要。

代案: `addJournal` の `opts.silent` のときは仕訳に `auto: 1` を立て、
ツアー判定を `journals.filter((j) => !j.sample && !j.auto).length` にする。
影響範囲は増えるが、2箇所の定義が1つの印で揃う。**こちらを推奨。**

### D-3. ファネルの段を組み直す（A-3・B-1 の修正）

ダッシュボード側（`scripts/admin/server.mjs`）のみの変更。アプリの再デプロイは不要。

現在の5段:
```
起動 → ログイン画面を見た → ゲスト開始 → 初回記帳 → 登録
```

変更案（入れ子が成立する4段）:
```
起動(app_first) → ゲスト開始(guest_first) → 初回記帳(first_journal) → 登録(registered)
```

`auth_view` は段から外し、「起動した人のうちログイン画面に当たった割合」として
**入口の内訳**を別に表示する。`?guest` で直行した人との比率が見えるようになる。

`journalOfGuest`（B-1）は分子分母が揃わないため**廃止**し、
ファネル内の「前段比」で読む形に一本化する。

### D-4. 表記の明確化（B-2）

「アクティベーション」に「訪問あたり（回数ベース）」と注記する。
`server.mjs` の文言修正のみ。

### D-5. 対応しないもの

- B-3（復元時に出ない）: 実害が小さく、対処するとインポートで一気に発火して
  かえって歪む。README に「復元経由では出ない」と明記するに留める
- B-4（リロードで二重）: 発生頻度が低い
