個人で[複式簿記の家計簿SaaS](https://kurofukubo.com/?utm_source=zenn&utm_medium=article&utm_campaign=scoring-loop)を運営しています。検索流入が伸びないので、改善計画をAIエージェントに作らせて、別のエージェントに採点させました。

51点。53点。48点。52点。

4回とも不合格です。毎回ダメ出しをプロンプトに書き足して投げ直したのに、点はほとんど動きませんでした。

## 毎回、違うところで落ちる

横ばいそのものより、落ちる理由が毎回入れ替わるのが気になりました。

1回目は、対象ページに「新規セクションを追加する」と書いてきました。開いてみたら既にありました。ファイルを読んでいません。3回目も同じことをやっています。

2回目は対照群の選び方です。効果を切り分けたいページと、対照に置いたページが、同じコミットで一緒に変更されていました。そのコミットはLPを24ページまとめて書き換えているので、比較になりません。

3回目は、まだクロールされていない変更の上に、さらに変更を重ねる計画でした。Coverageを見れば最終クロール日が変更日より前だと分かります。

4回目が個人的にいちばん堪えました。同じ文書の中に「順位を維持するだけで20〜30クリックは見込める」と書いておきながら、合格ラインを30に設定していたんです。何もしなくても達成できる条件を成功の定義にしていた。それから、達成不可能なほうもありました。「順位10以内かつ表示100かつクリック10」は、順位10前後の実測CTRが2〜3%なので算術的に成立しません。

数字のほうも似たようなものでした。

- 「順位10以内の合計460表示」と書いてきたが、サイト全体は457表示しかない。GSCの「ページ」と「クエリ」は同じ表示を別の切り口で数えているだけなので、足すと全体を超えます
- 経路別の内訳で「登録」列の合計が、そのイベントを出した distinct IP の総数を上回っていた。同じIPが複数のバケットに入っていた
- 「19表示から222表示、一桁増えた」。19は7日窓、222は28日窓の数字です。日割りにすると 2.71 → 7.93/日で、2.9倍

どれも指摘すればその場で認めて直します。指摘しなければ通ります。

## 禁止事項を足すのをやめた

4回目のダメ出しを書きながら、この足し算はいつ終わるんだろうと思いました。

禁止事項を書き足す戦い方は、次に踏む地雷を知っていることが前提です。同じ場所で落ちるならそれでいい。でも実際は毎回違う場所で落ちていて、しかも「対照群を同じコミットで変えるな」みたいな条件は、一度踏むまで思いつきません。禁止リストは事前には埋まらない。

なので、指示を磨くのをやめました。代わりに、出てきた計画を採点して差し戻すことにしました。採点基準なら、失敗の種類を列挙しなくても書けます。「全数値が一次データで再現できること」と書いておけば、まだ見たことのない種類の数値誤りもまとめて落ちる。

## 何を作ったか

指示書の構造を変えました。

まず、本文を書き始める前に埋めさせる事実の表を頭に置きました。

| # | 確認事項 | 確認方法 |
|---|---|---|
| A1 | 対象ページに、狙う語・セクションが既に無いか | ファイルを開いて全文読む |
| A2 | 対象ページの直近の変更履歴 | `git log --format="%h %ad %s" -- <path>` |
| A3 | その変更は本文か、タイトル/metaか | `git show <sha> -- <path>` で追加行を分類 |
| A4 | 対象ページの最終クロール日 | Coverageエクスポート。変更日より前なら未反映 |
| A5 | 対照ページが同じコミットで変更されていないか | `git show <sha> --stat --name-only` |
| A6 | 狙うクエリの現在の表示・順位・クリック | GSC クエリ.csv |
| A7 | その表示回数で、狙う変化を検出できるか | 検出力計算 |
| A8 | 対象ページからアプリへの実流入があるか | CloudFrontログ |

埋まっていない項目がある状態で施策を書くことを禁止し、埋められなかった欄は「未確認」と書かせて、それに依存する施策は提案させないことにしました。この「未確認と書いてよい」を明示しないと、埋められない欄を埋めるために推測が入ります。

A1とA4の2行だけで、4回のうち3回分の失敗が消える計算になります。

数値には検算を添えさせました。部分集合の合計を出したら全体と比較して載せる。内訳の各列の合計が、そのイベントのdistinct総数以下であることを確認して載せる。期間の違うデータは日割りにする。それぞれに、上に書いた実際の失敗例を1件ずつ付けています。抽象的な規則より具体例のほうが守られました。

検出力を先に計算させるのも入れました。率を p1→p2 に変える検出には、だいたい `16 × p̄(1-p̄) / (p2-p1)²` のサンプルが要る。足りないならその指標を合否判定に使わせない。うちは規模が小さく、日に動く端末が数えるほどしかないので、計算すると週合計でも49%未満の変化は検出できません。A/Bで効果を測るという選択肢が最初から無いわけです。これを先に出させると、測れないものを測れるように見せかける提案が出なくなりました。

採点は別のエージェントに渡しました。100点満点で、配点はこうです。

| 観点 | 配点 |
|---|---|
| 事実の正確さ | 30 |
| 検算の実施 | 15 |
| 因果主張の慎重さ | 10 |
| 判定設計 | 20 |
| 対象選定 | 10 |
| リスク | 10 |
| 実行可能性 | 5 |

事実の正確さと検算で45点。文章の良し悪しには1点も配っていません。4回の不合格が全部そこで落ちていたからです。冒頭に「根拠のない減点はしないこと。厳しく採点すること」と書いておかないと、採点役は褒めるか、理由なく辛くするかのどちらかに寄りました。

最後に停止条件を3つ。95点以上で合格。同じ種類の誤りが2回続いたら止めて人間が判断する。4回試して点が上がらなかったら、計画づくりをやめて、未確定の事実を人間が外部ツールで埋めるほうを優先する。

3つ目は51/53/48/52の一般化です。点が横ばいなのは計画が下手だからではなく、計画の入力になる事実が足りていない合図なので、そこで回すのをやめる。結局、人間の仕事は合否ラインを決めることと、この停止判断だけになりました。

## 落ち方が変わった

50点前後で横ばいだった頃と違って、どこが壊れているかが毎回名指しで出てくるようになりました。そして計画はそのまま v30 まで改訂が続いています。

版の履歴を読むと、ほとんどの版が前の版の撤回です。

- v9 — v8で決めた欠測の扱いに逆進性（条件によって必要な割合が下がってしまう）があったので撤回
- v20 — 簡易版の固定閾値が、自分で書いた禁止事項「無施策でも達成される水準を合格ラインにしない」を破っていたので撤回
- v25 — 再計算した検出力表から、表と逆の結論を書いていたので訂正

v25が象徴的でした。自分で作った表を自分で誤読して「精密版が上回るようになった」と書いている。表を見ると中位の条件では簡易版のほうが上で、逆転していません。

同じ時期に走らせていた記事の定性評価も似た経過をたどりました。こちらは第15版まで行って、版ラベル付きの撤回表が30行残っています。

| 版 | 撤回する主張 | 実際 |
|---|---|---|
| 2 | 対抗仮説は棄却できる | 循環論法。保留が正しい |
| 3 | 検出力81% | 点推定依存。37〜99%の幅がある |
| 6 | 検証結果を「支持された」に格上げ | 過剰。「整合的」が正しい |
| 9 | 修正案の変更範囲は2箇所 | 実際は8箇所 |
| 10 | 提案を利点だけで起草 | 手順を提案側にも広げた |

30行あります。誤りは消えませんでした。

ただ、ループを入れる前はこの30個が計画の中に残ったまま実行されていたはずで、そう考えると撤回表は失敗の記録というより、30回止まった記録ではあります。可視化されただけで解決はしていない、というのが正直なところです。

## 効かなかったもの

万能ではありませんでした。

文書を編集したら版番号と履歴を更新する、という取り決めをチェックリストに入れていたのに、v3→v4、v5→v6、v7→v8 と3回続けて漏れました。チェックリストは文書の末尾にあります。末尾は読まれない。文書の冒頭に「編集規約」として移してようやく止まりました。内容ではなく置き場所の問題だった、というのは気づくまで時間がかかりました。

もうひとつ、過剰主張そのものは禁止事項では止まりませんでした。記事評価のほうでは「小標本の点推定を既知の値として扱わない」といった規律を並べて、5個から6個に増やしています。それでも6版・7版で連続して同じことが起きました。文書に残っている総括はこれです。

> 規律は事後チェックであり、「苦労して取った証拠には見合う結論を出したい」圧力に勝てない。

効いたのは規律を増やすことではなく、書く順番を決めることでした。

> 新しい証拠を得たら、まず「この観察を同じく予測する対立仮説」を1つ書く。
> 自分の提案を書いたら、まず「その提案の欠点」と「不採用にした代案」を1つ書く。
> それを書き終わるまで、結論を書かない。

禁止事項は書いたあとに照らすものなので、書いてしまえば後付けの正当化ができます。順番を縛ると、正当化する前に反対側を書かされる。この違いに気づくのに、同じ仕組みで2回失敗しました。前半（証拠側）だけを先に入れていた時期があって、そのときは自分の提案が手順の適用外になり、9版・10版と2回連続で「利点4点・欠点ゼロ」の片面的な起草が通っています。後半（提案側）を足したのは11版でした。

## 結局、どこが変わったのか

最初の4回は、ファイルを開いていない、対照群が同じコミットで一緒に動いている、といったところで落ちていました。いまの計画が落ちるのは、欠測が出たときの閾値の引き方や、自分で作った検出力表の読み方です。

どちらも不合格には違いありません。ただ、前者は確認すれば防げるもので、後者は考えないと出てこないものです。落ちる場所が上に移った、というのがこの間に起きたことでした。点数の推移より、こちらのほうが変化として大きい。

人間の側に残った仕事は、思っていたより少なくなりました。合否ラインを決めることと、止めどきを決めること。計画の中身に口を出す回数は目に見えて減っています。

ただ、いちばん効いたのは採点ではなかった、というのが正直なところです。効果があったのは、本文を書く前に埋めさせた8行の表のほうでした。ファイルを開いたか。その変更はもう反映されているか。この2つを先に確認させるだけで、4回のうち3回分は起きません。ルーブリックは、そこをすり抜けたものを拾う網にすぎない。順序で防げるものを採点で拾おうとすると、コストだけが上がります。

小さな個人開発で検出力の話をしているのは滑稽に見えるかもしれませんが、規模が小さいほど、測れないものを測れるように見せかける誘惑は強くなります。少なくとも私は4回それをやりました。

そして、この仕組みの停止条件の3つ目は「4回試して点が上がらなければ、計画づくりをやめて、未確定の事実を人間が外部ツールで埋める」でした。指示書の末尾には、誰も出せていない項目が3つ並んでいます。経路別の転換率、検索需要の絶対値、競合SERPの構成。外部ツールを一度も見ていないので、AIには埋めようがありません。

いちばん重要な欄は、まだ私が埋めていない、ということです。ループを整備していた時間でキーワードプランナーを開けばよかったのかもしれない、とは思っています。
