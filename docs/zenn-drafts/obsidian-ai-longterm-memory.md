新しいセッションのClaude Codeは、先週あなたが何を決めたかを知りません。

「その方式は先月やめたはずでは？」と気づけるのは人間だけで、気づけなかった分だけ同じ検討を繰り返します。リポジトリの `CLAUDE.md` に全部足していくと、今度は「現在の仕様」と「過去の判断」が同じファイルで混ざり、どちらも読みにくくなります。

そこでリポジトリには「現在の正解」だけを置き、**「なぜそうしたか」はObsidianのVaultに置く**という分け方にしました。MCPサーバーもプラグインも使っていません。Claude Codeから見ればVaultはただのMarkdownのディレクトリで、Read・Grep・Globだけで足ります。

この記事は、その置き場所の作り方と、実際にAIの繰り返しを止められた例です。3プロジェクト・54ノートで運用している2026年9月時点のスナップショットです。

## 分界線：どちらに書くかを1つの問いで決める

最初にこれを決めないと、置き場所が2つある状態はただの二重管理になります。

| | 置き場所 | 性質 |
|---|---|---|
| 仕様・設計・実装・手順 | `C:\<project>\`（リポジトリ） | 常に上書きされる「現在の正解」 |
| なぜそうしたか / 調査と解釈 / 教訓 | `D:\obsidian\`（Vault） | 上書きせず積み上がる |

判定は一問だけです。

> **そのリポジトリが消えても価値が残るか？ → Yes ならVault、No ならリポジトリ。**

「DynamoDBのキー設計」はリポジトリ、「なぜRDBではなくDynamoDBにしたか」はVault。リポジトリの仕様書をVaultに転記してはいけません。パスでリンクするだけにします。ここを緩めると古い仕様の写しがVaultに溜まり、AIが古い方を読み始めます。

リポジトリ側の `CLAUDE.md` には、行き先を1行だけ書いておきます。

```markdown
## 長期知識（Obsidian）

仕様は本リポジトリが正。「なぜそう決めたか」「調査の解釈」「横断ノウハウ」は `D:\obsidian` にある
（起点: `D:\obsidian\01_Projects\<プロジェクト名>.md`、規約: `D:\obsidian\CLAUDE.md`）。
過去の判断の理由が必要なときはそちらを参照する。リポジトリの仕様書をVaultへ転記しないこと。
```

## Vault側の `CLAUDE.md`：AIに読ませる規約

Vaultのルートに置いている規約の中核です。そのままコピーして使えます。

```markdown
## 構造
00_Inbox/      未分類キャプチャ（分類を要求しない場所）
01_Projects/   プロジェクトハブ。1プロジェクト=まず1ファイル
02_Knowledge/  再利用可能な技術知識・ノウハウ・Postmortem
03_Decisions/  意思決定ログ  YYYY-MM-DD-slug.md
04_Research/   調査 + 自分の解釈  YYYY-MM-DD-slug.md
05_Ideas/      未着手アイデア
06_AI/         AI Context Layer（AIが最初に読む場所。事実の複製を置かない）
07_Daily/      YYYY-MM-DD.md
08_Meta/       Templates/ Dashboards/
99_Archive/    没プロジェクト・役目を終えたノート

## Properties 規約
全ノート必須: `type` `created` `updated`
条件付き: `project`（プロジェクト関連） `status`（project / idea のみ） `source`（research のみ）
`type` の値: project | idea | knowledge | decision | research | daily | ai-context | inbox
規約外のプロパティを勝手に追加しない。日付は `YYYY-MM-DD`。変更したら `updated` を必ず更新する。

## 情報取得ルール（読むとき）
1. まず `06_AI/Global-Context.md` を読む
2. プロジェクトの話なら `01_Projects/<名前>.md` を読む
3. 深掘りは frontmatter を grep する
   例: `grep -rl "project:.*BudgetBook" 03_Decisions/`
4. 索引ファイルを生成しない。grep が常に最新の索引である。

## 更新ルール（書くとき）
- 既存ノートは追記優先。上書きする前に必ず全文を読む
- Decision / Research のファイル名は `YYYY-MM-DD-` で始める
- 新しいノートは既存ノートへ最低1本 `[[リンク]]` を張る（孤立ノートを作らない）

## 禁止事項
- 秘密情報を書かない（APIキー / トークン / クラウドの認証情報 / 個人情報）。在処だけ書く
- `03_Decisions/` の既存ノートを書き換えない。覆すときは新しいDecisionを作り `supersedes:` を書く
- ユーザーの承認なしにファイルを削除・移動しない
- `06_AI/` に事実（数値・仕様）を書かない。原則と索引だけを置く
```

効いているのは**「Decisionを書き換えない」**です。書き換えを許すと、過去に何を却下したかが消えます。AIは消えた選択肢を平気で再提案します。

もう1つは**「索引ファイルを生成しない」**。AIに索引を作らせると、更新されないまま古い索引が残り、そこに載っていないノートは存在しない扱いになります。grepなら常に現在のファイルを見ます。

## `06_AI/`：AIが最初に読む1枚

ここには事実を書きません。「誰が・何を・どう作っているか」の輪郭と、詳細への行き先だけです。

```markdown
## 私について
- 個人開発者。企画・実装・インフラ・マーケティングまで一人。
- リソースは自分の時間だけ。「実装できるか」より「一人で運用し続けられるか」で意思決定する。

## AIの役割分担
- Obsidian = 長期記憶。決定の理由・調査の解釈・教訓
- GPT      = 思考・批判・壁打ち・レビュー
- Claude Code = 実装・実行
- GitHub   = コードの正史
```

隣に `AI-Usage-Rules.md` を置き、渡してよい情報の線引きを書いています。

> **Vaultはいずれ丸ごとAIに読まれる前提で書く。** 秘密情報は在処だけを書く。
> ✅ 「APIキーは Edge Function の secret に設定」
> ❌ `SERVICE_API_KEY=xxxxxxxx`

`Workflow.md` には一周の流れを書いています。大事なのは最後の1行です。

```
思いつき ──> 00_Inbox（分類しない）
                │  /obsidian-capture（週1）
                ▼
   05_Ideas / 04_Research / 02_Knowledge / 03_Decisions
                │
                ├──> GPTで壁打ち ──> 結論をVaultに戻す
                └──> Claude Codeで実装 ──> 実際の結果（ストア指標 / GA / Search Console）
                                              └─> Research or Knowledge に戻す
```

**一周して戻ってこないものは知識になりません。** 実装して終わり、調べて終わりにしないための図です。

## スキルは4本だけ自作する

Claude Codeのスキルとして、Vault操作を4つに絞っています。

| スキル | 役割 |
|---|---|
| `/obsidian-capture` | 引数ありならInboxに放り込むだけ。引数なしならInboxを仕分ける |
| `/obsidian-context` | Vaultを横断して読み、そのタスクに必要な分だけのブリーフを出す（読み取り専用） |
| `/obsidian-decision` | 決めたその日に意思決定を記録する |
| `/obsidian-research` | 調査結果を「自分の解釈」まで含めて保存する |

キャプチャ側で徹底しているのは**摩擦をゼロにすること**です。

```markdown
### 処理
3. 中身は最小限。分類を試みない。整形しない。
### 出力
作成したファイルパスを1行で報告するだけ。要約も分類提案もしない
```

要約や分類を返させると、投げるたびに確認が発生して、そのうち投げなくなります。分類は週1の整理モードでまとめてやり、そこでは承認前にファイルを1つも動かしません。

読み出し側（`/obsidian-context`）で効いているのは、出力形式を固定したことです。

```markdown
**縛られている決定**（実装で覆してはいけないもの）
- YYYY-MM-DD <決定> — 理由1行  [[ノート名]]

**Vaultに情報がない部分**
- （推測で埋めず、ここに正直に列挙する）
```

**最後の欄を必須にすると、AIが「知らない」と書くようになります。** ここが無いと、足りない前提が推測で埋まります。

構文知識だけは他人の資産を借りています。[kepano/obsidian-skills](https://github.com/kepano/obsidian-skills)（MIT）から、Obsidian記法と `.base` の構文を扱うものだけをコピーし、`VENDORED.md` に出所と「編集しないこと」を明記しています。

## 実際に繰り返しを止められた例

**1つめ。AIは工数を理由に要件を落とします。**

自分が作っている家計簿アプリ（[kurofukubo](https://kurofukubo.com/?utm_source=zenn&utm_medium=article)）のiOS初回審査で、Googleログインを出すなら代替ログインの併設が要る（Guideline 4.8）という指摘に当たりました。AIが並べた選択肢は、A「Sign in with Appleを追加（工数大）」、B「iOSではGoogleボタンを消す」で、推奨はBでした。動いている機能をプラットフォーム単位で削る案です。

実際にコードを読んだら、認証プロバイダを渡している箇所は1行で、ボタンを足すだけで済みました。「工数大」は調べる前に貼ったラベルで、それを根拠に要件を削る案が推奨になっていたわけです。Knowledgeノートにはこうルール化しました。

> 1. 工数を選択肢の優劣の理由にしない。併記するのは「いつ終わるか」だけ
> 2. 要件を満たす案を先頭に置く。満たさない案を推奨にしない
> 3. 見積もりを出すなら該当コードを読んでから

**2つめ。検証が「意図どおり動くか」しか測っていませんでした。**

別プロジェクトで、サーベイ出力に `collapseReason: {credit: 60}` ——60ケース全部が同じ理由で崩壊、という結果が出ていました。計測器は正しく動き、数字も出ていた。それでも「今回の変更の意図」に紐づく指標ではなかったため読み飛ばされ、数ラウンド後に凍結しました。

差は道具でも能力でもなく、見出し指標だけを読む習慣でした。是正は「テストを増やす」ではなく**既にある出力を敵対的に読む**こと。ノートには「ガード到達・単一値分布はデータではなくエラーとして扱う」「失敗しているスクショを1枚撮ることを成果物にする」と書いています。

どちらも、次に似た場面でAIに読ませれば同じところで止まれます。これが「消えたら価値が減るもの」の実体で、リポジトリには置けない種類の情報です。

## 積み上がるものには監査が要る

追記優先で書き続けると、壊れたリンクと孤立ノートが必ず出ます。月1で `/obsidian-health` を走らせ、次を検出だけさせています（**自動修正はさせません**）。

- 存在しないノートへの `[[リンク]]`
- どこからもリンクされていない孤立ノート
- `type` / `updated` の欠落、規約外の値
- 同じ話題が別々のノートに散っている重複

自動修正を許さないのは、リンク切れの正解が「リンクを消す」ではなく「**書くべきノートがまだ無い**」であることが多いからです。検出結果を見て、統合するか、書き足すかを人間が決めます。

決定を覆すときは、既存のDecisionを書き換えずに新しいノートを作り、frontmatterに `supersedes: [[旧ノート]]` を書きます。こうすると「却下 → 後で採用」の履歴が残り、**同じ選択肢を3回検討する事故が消えます**。

## 放置を見つける：Bases で一覧にする

ノートが増えると「書いたのに忘れている」が起きます。Obsidianの Bases（`.base` ファイル）で一覧を作っておくと、AIに聞かなくても目で気づけます。

プロジェクト一覧に入れているのは、**90日動いていないものに警告を出す式**だけです。

```yaml
filters: type == "project"
formulas:
  days_since: (now() - file.mtime).days.round(0)
  stale: if((now() - file.mtime).days > 90, "⚠️ 放置", "")
views:
  - type: table
    name: すべて
    groupBy:
      property: status
      direction: ASC
    order: [file.name, status, updated, formula.days_since, formula.stale]
  - type: table
    name: 稼働中のみ
    filters: status == "active"
```

ホーム側は、種別ごとに切ったビューを1枚に並べているだけです。

```yaml
filters:
  not:
    - 'file.inFolder("08_Meta")'
    - 'file.inFolder("99_Archive")'
views:
  - { type: table, name: "稼働中のプロジェクト", filters: { and: ['type == "project"', 'status == "active"'] } }
  - { type: list,  name: "Inbox（未処理）",      filters: 'file.inFolder("00_Inbox")' }
  - { type: table, name: "最近の意思決定",        filters: 'type == "decision"', limit: 10 }
  - { type: table, name: "最近の調査",            filters: 'type == "research"', limit: 10 }
```

Properties を規約どおりに書いてさえいれば、この一覧は勝手に埋まります。逆に言うと、**`type` を適当に付けた日から一覧は嘘をつき始めます。**規約を1枚に書いてAIに守らせる理由はここにもあります。

なお Bases の閲覧はObsidianアプリに依存します。Claude Code側の機能（Read / Grep / Glob）はアプリが無くても動くので、依存はここだけに閉じ込めています。

## リズム：書く日を決めておく

仕組みより、いつ書くかのほうが続きます。

| 頻度 | やること |
|---|---|
| 毎日 | Inboxに1行投げる。整形しない |
| 週1 | `/obsidian-capture` でInboxを空にする |
| 決めた日 | `/obsidian-decision` を走らせる |
| 月1 | `/obsidian-health` で監査、`/obsidian-synthesize` で散った知識を1本に統合 |

「決めた日」だけは後回しにできません。**判断の理由は、決めた瞬間から劣化し始めます。**1週間後に書くと、選ばなかった案の検討が抜け落ち、結論だけが残ります。結論だけのDecisionは、後から読んでも覆せません。

## 入れなかったもの

導入時にMCPサーバーとフレームワークを検討して、どちらも却下しました。Decisionノートから抜粋します。

| 案 | 却下理由 |
|---|---|
| Obsidian MCP / Local REST API | Obsidian常駐が必須。APIキー管理が増える。ローカルファイルにプロトコルを1枚挟む合理性がない |
| 大規模フレームワーク | 独自のVault思想を強制する。45コマンドは個人開発には過剰で、覚えられないものは使われない |

理由はこう書きました。

> Claude Codeから見ればVaultはただのディレクトリであり、Read / Grep / Glob で完結する。**依存を増やさないこと自体が、個人開発における最大の保守性**。フレームワークを入れないのは機能不足を許容するためではなく、他人のオントロジーを背負うと「書くたびに他人のルールを思い出す」摩擦が生まれ、続かなくなるため。

同じノートに撤回条件も書いています。

> grepベースの検索でノート数に対して実用速度が出なくなった場合（目安：1,000ノート超）、またはObsidian CLIで明確に楽になる自動化が具体的に発生した場合。

**撤回条件を書いておくと、「今は不要」という判断を後から見た自分が蒸し返さずに済みます。** 判断そのものより、判断が有効な範囲を書くほうが効きます。

## 始め方

最小構成なら、この3つで動きます。

1. Vaultのルートに `CLAUDE.md` を置く（上の「構造」「Properties規約」「情報取得ルール」「禁止事項」をコピー）
2. `06_AI/Global-Context.md` に、自分が何を作っているかと、詳細への行き先を書く
3. リポジトリ側の `CLAUDE.md` に、Vaultの起点パスを1行足す

スキルは無くても始められます。最初に効くのは `03_Decisions/` に1本目を書いた日です。**「決めた日に書く」だけは守ってください。** 後日の再構成は必ず劣化します。

## この運用で作っているもの

この記事の仕組みで開発・運用しているのが、複式簿記の家計簿 **[kurofukubo（黒福簿）](https://kurofukubo.com/?utm_source=zenn&utm_medium=article)** です。

費目ごとの支出と、口座残高の目的別の配分（生活費・旅行・税金の積立…）を、同じ1回の記帳で同時に管理できます。貸借対照表・損益計算書・純資産の推移まで自動で出ます。銀行連携なし・登録なしでブラウザから試せます。iOS版もApp Storeで配信予定です。

記事に出てきた「AIが工数を理由に要件を落とした」も「審査で食らった指摘」も、全部このアプリで実際に起きたことです。
