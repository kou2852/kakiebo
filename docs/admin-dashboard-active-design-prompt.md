# GPT 用プロンプト — 管理ダッシュボードに「稼働（DAU/WAU/MAU）」を足す

`docs/admin-dashboard-active-prototype.html` を添付して、以下をそのまま渡す。

---

## 依頼

添付した1枚のHTMLは、個人開発の家計簿SaaS「kurofukubo（黒福簿）」の**運営者だけが見る管理ダッシュボード**のモックです。localhost でだけ動き、見るのは**開発者1人**。数字を毎日ざっと眺めて判断するために使います。

このうち **`NEW` バッジが付いている「稼働」バンドが今回の追加分**で、それ以外は現行の画面をそのまま再現したものです。稼働のセクションを作ってみたものの**見にくくて使えません**。ここを設計し直してください。

**主眼は「稼働」バンドです。** それ以外のセクションは 2026-08-02 に整えたばかりなので大きく変える必要はありません。ただし、稼働を差し込んだことで生じた重複や順序の問題（後述の問題6）は直して構いません。

## 絶対に守ってほしい制約

1. **1枚の自己完結HTMLで返してください。** 外部CDN・Webフォント・画像・ライブラリの読み込みは一切不可（オフラインのlocalhostで開きます）。CSSは `<style>` に、JSは `<script>` にインラインで。グラフを描くなら CSS かインラインSVGで。
2. **HTMLの中でバッククォート（`` ` ``）と `${` を使わないでください。** 最終的に Node 製サーバー（`scripts/admin/server.mjs`）のテンプレート文字列に戻すため、使われると構文が壊れます。文字列連結は今と同じ `'...' + x + '...'` の形で。
3. **データ構造（プロパティ名）は変えないでください。** 後述のJSONがサーバーから来ます。並べ方・まとめ方・強弱・グラフの種類は自由です。
4. **表示している数字・項目を減らさないでください。** どれも見る目的があります。畳む・小さくするのは構いません。
5. **解釈やアドバイスの文言を足さないでください。**「改善しましょう」「良好です」等は不要です。数字だけを見せる方針です。
6. 冒頭のダミーデータ（`DAILY` / `WEEKLY` / `MONTHLY` ほか）は**体裁確認用**です。そのまま残してください（こちらで実データに差し替えます）。

## この数字の意味（ここを崩されると使い物にならない）

「稼働」は、端末側の localStorage に「どの窓まで送ったか」を持ち、**窓（日／週／月）ごとに一度だけ**サーバーへ送るイベントの件数です。したがって件数がそのまま「その窓で使った端末数」になります。

以下は**表示の都合で丸めたり統合したりしないでください。**

1. **単位は「人」ではなく「端末（ブラウザ）」です。** 同じ人がPCとスマホで使えば2、ブラウザのデータを消せば別端末になります。ラベルは「人」で構いませんが、端末単位であることが分かるようにしてください。
2. **アクセス回数ではありません。** 同じ端末が週に5日使っても、週次では1です。
3. **「全体」は内訳の合計ではありません。** 全体は端末ごとに1回しか送らないので重複なしの正確値。内訳4種はイベントごとに独立して立つため、同じ窓の中でゲスト→ログインに変わった端末は**両方に計上されます**。その差が `cv`（転換）です。`total = gn + gr + un + ur - cv` が常に成り立ちます。**この関係が読み手に伝わることが、このセクションで一番大事です。**
4. **週次・月次は日次の合計ではありません。** 別々に数えた独立の値です。
5. **「新規」の基準日が2種類あります。** 新規ゲストは初回利用日、新規ログインは初回ログイン日がその窓の中にあるか、で判定します。
6. **窓が表示期間からはみ出しているものは「途中」**です（当日・今週・今月、および期間の左端）。確定した窓と**一目で区別**できる必要があります。確定値と途中の値を同じ強さで並べると、必ず「落ち込んだ」と誤読されます。

## 今の問題（優先度順）

### 1. 積み上げ棒が細すぎて内訳が読めない
日別チャートが30本並び、1本あたり約35px。それを4色に割るので、値の小さい「新規ログイン」（0〜1）は**1px以下になって見えません**。日別で4分割を見せること自体に無理があるかもしれません。日別は全体の推移だけにして内訳は別の見せ方にする、期間を絞る、横向きにする等、**構造から考え直してください。**

### 2. KPIカードの内訳バーが機能していない
カード下部の6px の帯を4色に割っており、細い色が潰れています。装飾になっていて情報になっていません。

### 3. 「全体 ≠ 内訳の合計」という一番大事な注意が、見出しの小さな文字に埋もれている
上記「意味」の3番です。今は構成比セクションの `<small>` に押し込まれていて、まず読まれません。

### 4. 週次・月次のテーブルが8列あり、横に長い
スマホで横スクロールが出ます。列を減らさずに読ませる方法を考えてください。

### 5. 「途中」の表現が弱い
薄字＋小さなタグだけで、確定値との区別が一目で付きません。

### 6. 既存セクションとの単位の衝突
すぐ上の「いま」バンドに **実人数 312人**（期間全体の重複なしIP数）があり、稼働の **DAU 23人** と並びます。母数も判定方法（IP / 端末）も期間も違うのに、どちらも「人」で表示されるため混乱します。並べ方の整理、または「いま」側の項目の置き場所の変更を検討してください。

### 7. 稼働バンドだけ色数が多く、画面から浮いている
既存画面は `--ac`（ティール）のほぼ単色です。そこへ4色の系統を持ち込んだため、ここだけ賑やかになっています。**既存の落ち着いたトーンに馴染ませてください。** 4系統の区別が付けば、色以外の手段（濃淡・パターン・配置・ラベル）でも構いません。

### 8. セクションが縦に長い
稼働だけで4ブロック（KPI／日別／構成比＋転換／週次＋月次の表）あり、全体像を掴むのにスクロールが要ります。

## サーバーから来るデータ

```json
{
  "active": {
    "daily": [
      { "date": "2026-08-06", "total": 23, "gn": 9, "gr": 9, "un": 1, "ur": 5, "cv": 1, "partial": false }
    ],
    "weekly": [
      { "label": "07/27〜08/02", "total": 105, "gn": 62, "gr": 30, "un": 3, "ur": 12, "cv": 2, "partial": false }
    ],
    "monthly": [
      { "label": "2026-07", "total": 327, "gn": 218, "gr": 78, "un": 8, "ur": 30, "cv": 7, "partial": false }
    ]
  }
}
```

| キー | 意味 |
|---|---|
| `total` | 全体（重複なし） |
| `gn` | 新規ゲスト |
| `gr` | 既存ゲスト |
| `un` | 新規ログイン |
| `ur` | 既存ログイン |
| `cv` | 転換（その窓でゲスト→ログインに変わった端末。内訳の合計 − 全体） |
| `partial` | その窓が表示期間からはみ出している（集計途中） |

日次は最大90件、週次は最大13件、月次は最大4件です。実際の規模感は添付のダミーどおりで、DAU は十数〜数十、MAU は数百のオーダーです。**3桁で収まる小さな数字**なので、大きな数を捌く設計は不要です。

## 出してほしい数字

減らさない範囲で、まとめ方は自由です。

- **DAU / WAU / MAU** — それぞれ最新の確定した窓の値。途中の窓の値も併記
- **粘着度** — DAU/WAU、DAU/MAU、WAU/MAU（確定した窓どうしの比）
- **日別の推移** — 全体と、可能なら内訳
- **内訳の構成比** — 新規ゲスト／既存ゲスト／新規ログイン／既存ログイン
- **転換** — その窓でゲストからログインに変わった端末数
- **週次・月次の一覧** — 上記すべての列

## デザインの方向性

- アプリ本体と同じ配色を使ってください。CSS変数が定義済みです（`--ac` #0d9488 がブランド色）。**この配色は変えないでください。**
- 落ち着いた実用重視のトーン。装飾より**情報の階層**を優先してください。
- 主にPC（1280px前後）で見ますが、スマホ（390px）でも横スクロールが出ないようにしてください。
- ダークモードは不要です。
