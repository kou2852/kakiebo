## 1. 資産推移グラフ（優先度: 最高・工数最小）

### 現状
`netWorthTrend(journals, accounts, months = 6)` が実装済みで、ダッシュボードに「純資産の推移（直近6ヶ月末）」として既に表示されている。**BACKLOGの記載は実態より遅れている。**

### 不足している差分のみ
1. **目標線の設定**（BACKLOGの「目標線設定可」が唯一の未実装部分）
   - 目標純資産額をユーザーが設定できるようにする
   - 保存先: 既存の設定と同様に localStorage（ゲスト）/ DynamoDB（登録ユーザー）
   - グラフに水平の破線として重ねる
2. **表示期間の可変化**
   - 現在6ヶ月固定。12ヶ月・24ヶ月・全期間を選べるようにする
   - `netWorthTrend()` は既に `months` 引数を持つため、UIを足すだけ

### 工数の目安
小（1〜2日）。既存関数の拡張とUI追加のみ。

### 注意点
目標額の保存先を新設する場合、バックエンドに保存APIが必要か検討すること。既存の `/api/budgets` のように単純な値なら、そこに相乗りする選択肢もある。

## 2. 確定申告サポート（【却下】2026-08-01 ユーザー判断により実施しない）

以下は参考として残すが、**着手しない**。

### 却下前の内容（参考）

### 狙い
医療費控除・ふるさと納税の対象額を自動集計する。**LPの集客記事（`guide-medical-expense.html`・`guide-furusato.html`）と直結**しており、ふるさと納税は10〜12月、確定申告は2〜3月が需要ピーク。**今作れば秋の需要期に間に合う。**

### 設計方針
BACKLOGの案（「科目にタグ付けで対象を識別」）を踏襲する。既存のタグ機能（`splits` に `tagId` を持つ構造）が土台として使える。

### 実装内容
1. **控除カテゴリの定義**
   - `医療費控除` / `ふるさと納税` / `iDeCo` / `生命保険料控除` などを定義
   - 既存のタグとは別概念にするか、タグに「控除区分」属性を足すかは設計判断
   - **推奨**: タグに `deductionType` フィールドを追加する方が、既存のタグ付けUIをそのまま使えて実装量が小さい

2. **集計ロジック**（`utils/` に新規追加）
   - 年度を指定し、控除カテゴリごとに対象仕訳を抽出・合計
   - **医療費控除は計算式が必要**: `(医療費 − 補填額) − min(所得×5%, 10万円)`
     - 補填額（保険金等）の扱いをどうするか要検討。別タグにする案が現実的
   - ふるさと納税: 寄附額の合計と自己負担2,000円を差し引いた控除見込み額

3. **レポート画面の新設**
   - `components/Reports/TaxPage.jsx`（新規）
   - サイドバーの「レポート」セクションに追加（`config/nav.js`）
   - 年度切替、カテゴリ別の対象額一覧、明細の展開表示
   - CSV/PDF出力（既存の `utils/csv.js`・`utils/pdf.js` を再利用）

### 工数の目安
中（1〜2週間）。集計ロジックの正確性検証に時間を要する。

### 重大な注意点
**税務上の正確性が問われる領域**。以下を必ず守ること。

- 計算結果は「概算」「参考値」であることを画面に明記する
- 「この金額で申告できます」といった断定表現を使わない
- 制度の細かい要件（生計を一にする親族、上限額、所得による変動）を完全には反映できないことを明示
- LP記事と同様、「税務上の取り扱いは税務署・税理士に確認を」の注記を入れる

誤った金額を断定的に表示すると、ユーザーが実害を被る可能性がある。

## 3. モバイル最適化（優先度: 高・ただし前提の確認が必要）

### 現状
- レスポンシブCSSは実装済み（`global.css` の `@media (max-width: 768px)`）
- 本セッションの検証で、360px幅でも主要画面に横スクロールは発生していないことを確認済み
- つまり「表示が崩れる」問題ではなく、**「スマホでの操作性」の改善**が課題

### BACKLOGの案
1. スワイプでカテゴリ選択するクイック入力UI
2. ボトムシートモーダル（下から出す。親指が届く）
3. フローティング「+」ボタン（右下固定）

### 評価と推奨順序

**① フローティング「+」ボタン（推奨・工数小）**
- 記帳への導線が常に画面内にある状態を作る
- activation（記帳到達率）の改善に直結する可能性が高い
- 実装は既存の `mcta`（LPのモバイル固定CTA）と同様の手法で可能

**② ボトムシートモーダル（推奨・工数中）**
- 既存の `Modal.jsx` に `bottomSheet` オプションを足す形が現実的
- 全モーダル（仕訳入力・科目追加・CSV取込等）に一括で効く
- スマホでの入力体験が大きく変わる

**③ スワイプでカテゴリ選択（保留を推奨）**
- 実装コストが高く、学習コストもユーザーに強いる
- 既存の「かんたんモード」「プリセット」で同じ目的をある程度満たしている
- ①②の効果を見てから判断すべき

### 前提の確認結果（2026-08-01 実施済み）

## 4. 家族アカウント・権限管理（優先度: 最低・現時点では非推奨）

### 現状
- テナント分離は `PK = USER#<userId>` に固定（`backend/src/lib/db.js`）
- 全データがユーザー単位で完全分離されており、**共有の概念が一切ない**

### 必要な作業の規模

これは他の3機能とは次元が違う大規模開発になる。

1. **データモデルの変更**
   - BACKLOG案の `PK=FAMILY#<familyId>` を導入
   - 既存ユーザーのデータ移行が必要（本番稼働中のため慎重を要する）
   - 個人帳簿と共通帳簿の切り替えロジック

2. **招待フロー**
   - 招待メール送信 → **SESの本番申請が必要**（現在サンドボックス状態の可能性）
   - 招待トークンの発行・検証・期限管理

3. **権限管理**
   - 閲覧のみ / 入力可 / 管理者の3階層
   - APIの全エンドポイントで権限チェックを追加（`journals` `accounts` `settings` すべて）

4. **E2E暗号化との整合**
   - **最大の技術的困難**。現在のE2E暗号化はユーザー単位の鍵で暗号化している
   - 家族で共有するには鍵の共有機構（鍵交換・メンバー追加時の再暗号化・メンバー削除時の鍵ローテーション）が必要
   - これは暗号設計の変更であり、設計を誤るとデータ消失や情報漏洩に直結する

### 工数の目安
大（1〜2ヶ月）。E2E暗号化との整合だけで数週間かかりうる。

### 【2026-08-01 追記】E2E暗号化と排他にする設計（採用決定・実装は保留）

ユーザーの提案により、**家族アカウントとE2E暗号化を排他（どちらか一方のみ）にする**方針を採用する。これにより上記4の「E2E暗号化との整合」という最難関が丸ごと不要になる。

調査で確認した事実:
- E2E暗号化は**オプトイン**（設定画面で任意に有効化する機能。既定は無効）
- 保存単位は `getItem(userId, 'ENCDATA')` = **ユーザー単位の暗号文ブロブ**
- 有効化時は `clearPlaintext` でサーバー上の平文を削除している

排他にした場合のデータの持ち方:

| | データ | 鍵 |
|---|---|---|
| E2E利用者 | `PK=USER#<userId>` に暗号文 | 本人のみ |
| 家族利用者 | `PK=FAMILY#<familyId>` に平文 | 不要 |

**鍵交換・メンバー追加時の再暗号化・削除時の鍵ローテーションがすべて不要**になり、工数は1〜2ヶ月 → 3〜4週間程度に下がる。

排他にしても残る課題:
1. **招待メールにSESの本番申請が必要**（サンドボックス解除の審査に日数がかかる外部依存）
2. 全APIエンドポイントへの権限チェック追加
3. 個人帳簿と共通帳簿の切替UI
4. E2E利用者が家族に参加する場合の解除導線（復号を伴う慎重な操作）

### 現時点で着手を推奨しない理由

**登録ユーザーが6人の段階で、複数人で使う機能を作るのは順序が逆。**

- 家族機能は「1人で使って価値を感じた人」が次に求めるもの
- 現在のボトルネックは流入量（1日10人）と定着であり、共有機能ではない
- 1〜2ヶ月を投じるなら、その間に流入・定着の改善を進める方が期待値が高い

**判断基準**: 登録ユーザーが数十人規模になり、かつ「家族と共有したい」という要望が実際に複数寄せられてから着手する。

**再検討の材料**（アンケート機能のデプロイ後に見る）:
