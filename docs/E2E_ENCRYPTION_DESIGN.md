# E2E（クライアント側）暗号化 設計書 — ゼロ知識アーキテクチャ

最終更新: 2026-06-16 / ステータス: **設計（未実装）**

## 0. 目的・脅威モデル

**目的**：家計データを**ユーザーの端末側で暗号化してから保存**し、運営者（個人開発者）も AWS も**平文を復号できない**状態にする（ゼロ知識）。

| 守る | 守らない（スコープ外） |
|---|---|
| 保存データ(DynamoDB)からの平文読み取り（運営者/AWS/漏洩時） | 侵害された端末・ブラウザ拡張・キーロガー |
| 通信経路（既にHTTPS） | ユーザー自身がパスフレーズを漏らす運用ミス |
| バックアップ/ログからの平文流出 | 一部メタデータ（後述：件数・更新時刻など） |

**前提が活きる点**：簿記計算はすでに全部クライアント側。サーバーは「保存」が中心なので、**サーバーを暗号文ストアにしても機能が成立**する。

---

## 1. 鍵設計（エンベロープ暗号）

```
パスフレーズ ──Argon2id(salt)──▶ KEK ──wrap──▶ [DEK] ──AES-GCM──▶ 各アイテム暗号化
リカバリーキー ─Argon2id(salt2)─▶ RKEK ─wrap─▶ [DEK]   （復旧用に別ラップ）
```

- **DEK（Data Encryption Key）**：ランダム256bit。全アイテムの暗号化に使う唯一の鍵。
- **KEK（Key Encryption Key）**：ユーザーの**暗号化パスフレーズ**から Argon2id で導出。DEK をラップ（暗号化）して保存。
- **リカバリーキー**：登録時にランダム生成しユーザーへ一度だけ提示（保管必須）。これでも DEK を別ラップ。**パスフレーズ忘れ時の唯一の復旧手段**。
- パスフレーズ変更時は **DEK を再ラップするだけ**（全データ再暗号化は不要）。

> ⚠️ **リカバリーキーは必須**。ゼロ知識では運営者がリセットできない＝無ければパスフレーズ忘却で全データ消失。

### サーバーに保存する鍵関連（いずれも平文鍵は含まない）
`PROFILE`（または `KEYS#v1`）に：
```jsonc
{
  "enc": { "v": 1, "kdf": "argon2id", "kdfParams": {"m":65536,"t":3,"p":1},
    "salt": "<b64>", "wrappedDEK": "<b64 nonce+ct>",
    "recoverySalt": "<b64>", "recoveryWrappedDEK": "<b64 nonce+ct>" }
}
```

---

## 2. 認証と暗号鍵の分離（重要）

- **認証**＝Cognito（SRP / Google OAuth）は従来どおり。
- **暗号鍵**＝Cognito とは独立した「**暗号化パスフレーズ**」を全ユーザーに設定させる。
  - 理由：(1) Google ログインはパスワードが無い、(2) Cognito パスワードはログイン後にクライアントから取得できず、リセットでデータ消失する。→ **認証と暗号化を別物にするのがベストプラクティス**。
- フロー：ログイン → パスフレーズ入力 → KEK 導出 → DEK 復号 → **セッション中はメモリ/IndexedDB に保持**（再入力を減らす。ログアウトで破棄）。

---

## 3. 暗号方式・ライブラリ

- **推奨**：`libsodium.js`（Argon2id ＋ XChaCha20-Poly1305 / secretbox）。枯れていて誤用しにくい。
- **代替（依存を増やさない）**：Web Crypto API（AES-256-GCM ＋ PBKDF2-SHA256 600k+ 反復）。Argon2 が使えない分 KDF が弱い。
- 各アイテムごとに**ランダム nonce**（GCM:96bit / XChaCha:192bit）。nonce は暗号文に前置して保存。
- **自前で暗号アルゴリズムを書かない。**

---

## 4. データモデル（保存形式）

### 方式A：完全ゼロ知識（推奨）
各アイテムを「SK（種別#id, 平文）＋暗号文」で保存。**日付も暗号化** → サーバーの GSI 日付検索は廃止し、**全件ロードしてクライアントで絞り込み**（個人規模で問題なし）。

```jsonc
// 例: JOURNAL#<id>
{ "PK":"USER#<sub>", "SK":"JOURNAL#<id>", "v":1,
  "ct":"<b64 nonce+ciphertext>",   // {date, desc, lines:[...]} を暗号化
  "updatedAt":"..." }              // 同期用の最小メタのみ平文
```
- 暗号化対象：journals / tags / wallets / budgets / presets / recurring / allocs（＋希望なら accounts 科目名も）。
- 平文メタ：PK/SK（id）, v, updatedAt のみ。→ **漏れるのは「件数」「更新時刻」程度**。

### 方式B：メタ保持（日付検索を残す）
`date` だけ平文にして GSI を維持し、`desc`/`lines`(金額・科目) を暗号化。
- 利点：サーバー側の期間検索・将来のサーバー集計が一部可能。
- 欠点：**取引日と件数が漏れる**（金額・内容は守られる）。ゼロ知識性は方式Aより弱い。

> 推奨は**方式A**（旗印「運営者でも見られない」を最大化）。実装簡易さ優先なら方式B。

---

## 5. サーバー側の変更

- 各 CRUD/保存エンドポイントは**暗号文をそのまま保存**するだけに（内容バリデーション不可）。
  - ⚠️ `journals.js` の**借貸一致チェックはサーバーでは不可能**になり、**クライアント側検証のみ**に。整合性はクライアント責任へ移る点を明記。
- 方式A採用時は **GSI1（日付）クエリを廃止**し、`/api/journals` は全件（必要ならカーソルページング）で暗号文を返す。
- 鍵メタ保存/取得用に `PROFILE` 拡張 or `GET/PUT /api/enc`（鍵バンドル）を追加。
- **平文・パスフレーズ・KEK・DEK は絶対にサーバーへ送らない/ログに出さない。**

---

## 6. 既存データの移行

1. ユーザーが「最高プライバシーモード」を有効化。
2. クライアントが**全データを取得（現状は平文）** → DEK 生成 → 各アイテム暗号化 → **一括アップロード**（`/api/import` 拡張 or 専用一括 PUT）。
3. `PROFILE.enc` に鍵バンドルと `encrypted:true` を保存。リカバリーキーを提示・ダウンロードさせる。
4. 以後ログイン時はパスフレーズで解錠。**無効化（復号して平文へ戻す）も用意**するとロックインを避けられる。

---

## 7. 段階的ロールアウト

- **Phase 1a**：オプトインの「最高プライバシーモード」。既定OFF。リカバリーキー運用に慣らす。
- **Phase 1b**：新規ユーザーは既定ONを検討（パスフレーズ設定を登録フローに組み込む）。
- LP `security.html` の「今後の予定」を「提供開始」に更新。

## 8. UX 要件

- **パスフレーズ設定**画面（強度メーター・確認入力）。
- **リカバリーキー**：生成・ダウンロード/印刷・「保管しました」確認チェック。
- **解錠**画面（ログイン後）。端末記憶オプション（IndexedDB、ログアウトで消去）。
- **パスフレーズ忘れ**：リカバリーキーで解錠→再設定。どちらも無ければ**復旧不可**を明記。
- 既存機能（エクスポート/インポート/アカウント削除）との整合。

---

## 9. アンチパターン（やらない）

- 暗号アルゴリズムの自作。
- パスフレーズを鍵として直接使用（必ず KDF 経由）。
- 鍵・パスフレーズ・平文をサーバー送信/保存/ログ出力。
- 「保管時暗号化（AWS KMS）」を「運営者が見られない」と訴求（KMS は運営者が復号可能＝ゼロ知識ではない。**claim は正確に**）。
- リカバリーキー無しでの本番投入（＝サポート不能なデータ消失多発）。

---

## 10. トレードオフ（合意事項）

- パスフレーズ再設定での自動復旧は不可（リカバリーキー前提）。
- サーバー側の横断検索・将来の**サーバー側AI分析/集計は制限**（クライアント側 or 暗号化解除前提に）。
- 実装・運用が複雑化。**バグると復号不能**＝エンベロープ暗号・リカバリーキー・枯れたライブラリで堅牢化必須。
